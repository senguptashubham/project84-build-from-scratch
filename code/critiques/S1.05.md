#### S1.05-1 · Class set comes from `y_true` only
- **Tag:** edge-case
- **Where:** code/sprint1_numpy_data_fluency/s1_05_classification_metrics.py, lines 20, 53, 86 (versus line 120)
- **What:** `get_precision`, `get_recall` and `get_f1` loop over `np.unique(y_true)`. `get_confusion_matrix` uses the union of true and predicted labels. Suppose a label appears in `y_pred` but never in `y_true`. Its false positives are never counted, and it gets no entry in the macro or weighted average. What do you expect micro precision to equal for a multiclass input? What does it equal here when a predicted-only class exists?
- **Why it matters:** the precision, recall and F1 functions disagree with the confusion matrix and with `sklearn` (which uses the union of labels). Macro, weighted and micro results come out wrong in this case, and no test would notice.
- **My answer:** Fixed: labels now come from the union of true and predicted labels. (Inferred from the code change, recorded 2026-10-23.)

#### S1.05-2 · Binary positive label is guessed from the data
- **Tag:** possible-misconception
- **Where:** same file, lines 44, 77, 113
- **What:** in the `binary` branch the positive class is "the largest label seen in `y_true`". If `y_true` happens to be all 0, the positive class becomes 0. If the input has three classes, the default quietly returns the score for the largest one instead of raising an error. I base "possible misconception" on the fact that `sklearn` fixes `pos_label=1` instead of inferring it. Is inferring it intended?
- **Why it matters:** the result depends on which labels happen to be in a given sample. One fold or batch can silently measure a different class from the next.
- **My answer:** Will switch to the largest sorted label ([-1]) and raise ValueError("Expected 2 unique labels for binary classification") when more than 2 distinct labels. (Recorded from chat, 2026-10-23.)

#### S1.05-3 · Zero denominators in the micro averages
- **Tag:** stability
- **Where:** same file, lines 32, 101 (and 65 for recall)
- **What:** per-class precision guards against `tp + fp == 0`, but the micro versions divide totals without a guard. The spec says to return 0 when nothing is predicted. Walk through `y_true=[0,0]`, `y_pred=[1,1]` (or an empty array) with `average='micro'`. What is returned, and are any warnings raised? Accuracy has the same unguarded division by `len(y_true)`.
- **Why it matters:** you get `nan` and a runtime warning where the spec asks for 0. Then `nan` spreads into anything that averages these scores, such as cross-validation.
- **My answer:** Fixed: zero denominators now return 0 in the micro, macro, weighted and accuracy paths. (Inferred from the code change, recorded 2026-10-23.)

#### S1.05-4 · Averaging block sits inside the loop in `get_recall`
- **Tag:** necessity
- **Where:** same file, lines 63-79
- **What:** in `get_precision` and `get_f1` the `if average == ...` block comes after the loop. In `get_recall` it is indented inside the loop. It is recomputed for every label, and only the last iteration's value is returned. Is this deliberate? What happens if `y_true` is empty, so the loop never runs and `recall` is never assigned? Related: `get_confusion_matrix` makes `k²` passes over `n` samples and returns a float matrix, and `get_TN` is never used. Do you need them?
- **Why it matters:** the answer is right only because the last iteration happens to be correct. The same mistake with a different average, or an early `break`, would give wrong results. The extra passes make the work grow with `k²·n` instead of `n`.
- **My answer:** Deferred: tried a couple of approaches to a faster confusion matrix without success; will revisit later, not investing more time now. (Recorded from chat, 2026-10-23.)

#### S1.05-5 · Tests do not match the spec's test line
- **Tag:** test-gap
- **Where:** code/sprint1_numpy_data_fluency/test_s1_05_classification_metrics.py, lines 10-14, 21, 28, 35, 42
- **What:** the spec asks for "five random cases, including one where a class has no predictions", compared with `zero_division=0`. The tests use two fixed hand-written arrays and no random generation. The binary tests do not pass `zero_division=0`. There is no binary case where nothing is predicted positive, no case with a predicted-only class (see S1.05-1), no string labels, and no binary confusion matrix. The comparisons use `np.isclose` defaults, whereas the repo rule states a default tolerance of 1e-6. Which of these gaps would have caught S1.05-1 and S1.05-3?
- **Why it matters:** passing tests give false confidence. The cases most likely to expose bugs are the ones missing.
- **My answer:** Fixed tolerance and zero_division in the tests. Single-class judged covered by the zeros/ones arrays already used; empty input not tested because sklearn rejects it; string labels skipped as Python knowledge rather than ML. (Recorded from chat, 2026-10-23.)

#### S1.05-6 · Binary default crashes when only one label is present
- **Tag:** edge-case
- **Where:** s1_05_classification_metrics.py, lines 44, 77, 113
- **What:** `sorted(keys)[1]` needs at least two distinct labels across `y_true` and `y_pred` together. With `y_true=[1,1]`, `y_pred=[1,1]` or all zeros, `get_precision` raises `IndexError: list index out of range`. Before, it returned a value. What should a one-class batch return, given that sklearn returns a number here? How does this relate to the positive label being guessed from the data rather than fixed?
- **Why it matters:** a perfect or all-negative fold, a small batch or a single class in a validation split is common. A metric function that crashes on it will take down whatever calls it, such as cross-validation from S1.04.
- **My answer:** Accept: switching to [-1], so a one-class batch scores that single label as positive. (Recorded from chat, 2026-10-23.)

#### S1.05-7 · Random test cases are not seeded
- **Tag:** test-gap
- **Where:** test_s1_05_classification_metrics.py, lines 16-26
- **What:** `default_rng()` has no seed, so every run draws different arrays. Also, the cases are built at import time, and the ranges decide what each tests: case 1 has disjoint label sets, case 2 has predictions confined to the middle of the true range, and so on. If one fails, can you reproduce it? Does each range really produce the situation you meant (a class with no predictions, a predicted-only class)? The spec says five cases and there are four.
- **Why it matters:** a rare failure can pass on re-run and cannot be debugged. The spec's five-case requirement is also not literally met.
- **My answer:** Changed rng to a fixed seed (42). Five-case count and range design not addressed. (Recorded from chat, 2026-10-23.) Decision: staying with four cases, will not add a fifth; considered sufficient. (Recorded from chat, 2026-10-23.)
